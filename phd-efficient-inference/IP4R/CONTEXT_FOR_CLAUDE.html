splash_frame definition

The splash_frame is the canonical all-segments-on LCD state that Phase-B detection must capture. A GOOD unit's splash_frame shows every 7-segment digit as 8 and every icon illuminated simultaneously.

Idle / Phase-A state

Before t ≈ 14 s, the remote shows its normal operating display — actual temperature/time values, only active-mode icons lit. This is Phase-A. The phase classifier (_classify_phase()) gates out these frames before LightGBM scoring.

    Root cause diagnosis (video 201351)

    Phase-B frames detected:  168
register() returned None: 122  ← 73% — ORB finds no keypoints on dark frames
C_ref < 5.0 (dim):         18
Valid frames:              28  (server sees 9 via SCAN_STEP=3)
C_ref: bimodal — near-dark most frames, bright spikes occasionally
    Sep-09 black jig (frame_median ≈ 48–50) vs Jul-14 lighter jig (≈ 76–78). Phase-B starts at t=0 — no Phase-A.
    Central finding: ORB+ECC registration is re-solved per frame. On dark frames, ORB finds no keypoints → register() returns None → frame dropped. The geometry is physically constant per video — re-solving per frame is the architectural bug.

    Secondary hypothesis: PWM backlight aliasing against 12 fps → bimodal C_ref.

4Two Remaining Sep-09 Failures

📹 Video 201454 — ABSTAIN

n_b = 2 phase_b frames reach LightGBM. EVIDENCE_MIN = 1.5 requires n × (fail_ratio − 0.5) ≥ 1.5 — with 2 frames this is never met. Server defaults to ABSTAIN.

Root cause: phase classifier is not finding Phase-B frames. Frame-count problem, not a LightGBM problem.

📹 Video 202145 — wrong FAIL

n_b = 5 frames, gate = classifier, LightGBM outputs FAIL. LightGBM trained on Jul-14 + Aug-28 brightness regimes. Sep-09 lit LCD features (nc(e), seg_cov, icon_cov) fall outside training distribution.

Root cause: Domain gap in feature distribution — model misclassifies a genuinely GOOD Sep-09 video.
